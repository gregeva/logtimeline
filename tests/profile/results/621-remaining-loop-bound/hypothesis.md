# Hypothesis — #621, the read loop's remaining run-constant bound

Written 2026-10-13T14:55Z, before the first timing run.

## What is being investigated

The case for generating the read loop's body per run rests on a bound the
#342 audit computed on 2026-09-26 (`features/342-redundant-logic-surfaces-audit-report.md`
§ Item 8, part 3; `tests/profile/results/342-read-loop-cost-curve/analysis.md`
§ The ceiling): about 64 tests of run constants per included line on the
default scenario, at 23 ns per boolean test, about 13 % of the access log's
time and 19 % of the application log's. Since then the hoisting work (#620,
PR #707) turned the loop's string compares into booleans, guarded the
user-defined-metric loops, put the per-file index blocks behind a demand flag,
looked the message and bucket entries up once and put the numeric filter
bounds behind one flag. The question is how much of the bound remains on
`release/0.19.0` at 524a66d, measured the way the audit measured it: the count
of run-constant tests an included line evaluates, times the cost of one test,
over the time per line.

## The count (taken before the timing runs)

NYTProf line counts of the loop on the first 100,000 lines of each benchmark
file, under the benchmark runner's invocation (every line is included on both):
`prototype/621-remaining-loop-bound/sites.tsv` classifies each executed line,
`tally.pl` sums the tests per included line.

| class | access log | application log |
|---|---|---|
| fixed for the run, removable by a body generated for the default options | 51 | 35 |
| fixed for a file or a format (removable only by a body per file or format) | 12 | 12 |
| first-observation latches over data | 6 | 4 |

The application log's lines carry no duration or bytes, so its lines skip the
per-message and per-bucket metric blocks and with them most of the tests.

## Hypotheses

**H1 (the per-test cost has not moved).** One always-false boolean test at the
every-included-line point still costs about 23 ns per line on both files:
the hoisting changed which tests the loop carries, not what a test costs.
Predicts: least-squares slopes over N in {0, 10, 20, 40} within ±3 ns of the
audit's 23.0 and 22.8 ns.

**H2 (the time per line has fallen).** The hoisting drops measured −4.94 %
and −1.80 % on the access log among others, so its time per line is below the
audit's 11.6 µs; the application log's is near the audit's 7.6 µs.

**H3 (the remaining bound is about 10 % and 11 %).** 51 tests × 23 ns over
roughly 11 µs is about 10.7 % on the access log; 35 × 23 ns over roughly
7.5 µs is about 10.7 % on the application log. Any reading under 3 % on both
files would mean the generated body no longer pays for its recorded costs.

## Method

Probes are generated by `prototype/621-remaining-loop-bound/make-probes.pl`
from the branch's `ltl` (the audit's gate series, re-cut because the audit's
generator also builds a hoist probe whose landmarks are gone): `gate-10`,
`gate-20`, `gate-40` insert N lines of `if ($probe_false) { $probe_sink++; }`
after `$total_lines_included++;`. Each probe's output and bare `-V` on both
100,000-line slices was compared with the base before any timing run: only the
total-time line and the no-match sampling time differ.

Timing is `prototype/342-read-loop-cost-curve/run-curve.sh` unchanged: ten
order-balanced rounds, the benchmark runner's invocation, the tool's own
`TIMING total`, on the day of web-server access log (761,698 lines) and the day
of application log (479,904 lines). Summarised by the audit's `summarise.pl`.
