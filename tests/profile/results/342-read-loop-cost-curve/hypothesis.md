# Hypothesis — #342 item 8, the per-line loop's cost curve

Written 2026-09-26T17:27Z, before the first run.

## What is being investigated

`read_and_process_logs()`'s per-line loop (`while (1) {` to the brace before
`close $fh;`, 1,345 physical lines at 0.19.0) carries about 107 tests of values
that are constant for the run: activation gates, option-shaped branches, string
compares on capture modes, and three `foreach` loops over a list that is empty
when no user-defined metric is configured. The #567 post-release finding
(`tests/profile/results/567-access-log-regression/analysis.md`) measured a
correctly gated, non-executing addition at +1.61 % on `single-day-access-log-standard`
(median of ten interleaved rounds, 8.985 s to 9.130 s) and 0 % on
`single-day-application-log-standard`, with both binaries executing the same 114
statements per line: the cost was the loop growing, not code running.

The question is the cost curve, not a reading: what one more run-constant test on
the every-included-line path costs, whether the form of the test (a boolean
scalar, a string compare, a hash lookup) is a separate cost class, and what the
cheapest remedy (hoisting the existing string compares and the unguarded loops)
recovers. The two remedies the architect named (generate the loop body per run;
hoist per-line option handling) are then assessed against the measured ceiling,
on paper.

## Hypotheses

**H1 (linear per-gate cost).** Each always-false boolean scalar test inserted at
one fixed point on the every-included-line path adds a constant cost per line,
so the total time grows linearly in N. Predicts: medians at N = 0, 10, 20, 40
lie on a line whose slope is resolvable at N = 40 even if the N = 10 step is
inside the round-to-round spread. From #567 (about five gates and branches for
+1.6 %), the slope is expected near +0.3 % per gate on the access log, so N = 40
should read near +10 %.

**H2 (form is a cost class).** A string compare (`$x eq 'bin'`) and a hash
lookup (`$h{x}`) each cost more per test than a boolean scalar read, because
each does more work per evaluation (a string comparison; a hash probe). Predicts:
at equal N the string and hash series read above the boolean series, and their
slopes are steeper.

**H3 (the hoist recovers its share of the slope).** Replacing the loop's
string-compare gates (five on the message-stats capture mode, three on the
bucket-stats mode, one each on the heatmap and histogram modes, five on the
grouping sensitivity) with booleans resolved before the loop, and placing the
three unguarded `foreach` loops over `@udm_configs` behind one boolean, is
behaviour-neutral and recovers no more than the per-test slope of H2 times the
number of tests changed. Predicts: a small negative delta on the access log,
bounded by the H2 slope times fifteen, and a smaller one on the application log.

**H4 (the family split follows loop share).** The application log spends a
smaller share of its time inside the loop body (1.11 s of 1.70 s exclusive in the
#567 profile, against 1.66 s of 2.63 s for the access log), so every probe's
percentage delta is smaller on it. Predicts: the same absolute cost per line and
a smaller percentage. The ScriptLog family, predicted in the #567 analysis to
behave like access logs because it too lives in the loop body, is checked with
one pair (base against N = 40).

## Method

Probe binaries are behaviour-neutral edits of the base `ltl` at the issue
branch's head (version stamp `0.19.0`), generated by
`prototype/342-read-loop-cost-curve/make-probes.pl` from the base file, never
hand-edited:

- **Gate series** `gate-10`, `gate-20`, `gate-40`: N lines of
  `if ($probe_false) { $probe_sink++; }` inserted immediately after
  `$total_lines_included++;` (the every-included-line point), with the two
  scalars declared at file scope.
- **Form series** `str-10`, `str-20`, `str-40` (`if ($probe_mode eq 'bin') { ... }`,
  the mode holding `'raw'`) and `hash-10`, `hash-20`, `hash-40`
  (`if ($probe_hash{x}) { ... }`, the value 0), same point.
- **Hoist probe** `hoist`: the fifteen string compares named under H3 replaced by
  booleans computed once before the per-file loop, and the three `foreach`
  loops over `@udm_configs` wrapped in `if (@udm_configs) { ... }`. The
  generator asserts the exact number of substitutions.

Behaviour neutrality is proven before any timing run: `perl -c` on every probe,
and every probe's output and bare `-V` sections diffed against the base on two
fixtures (`tests/fixtures/numeric-highlight-boundary.txt` and
`tests/fixtures/tomcat-access-single-sample-keys.txt`), with the timing and
memory lines excluded from the diff.

**Timing runs.** `prototype/342-read-loop-cost-curve/run-curve.sh`: eleven
candidates (base plus the ten probes), ten rounds, on
`single-day-access-log-standard` (148 MB access log) and
`single-day-application-log-standard` (85 MB application log), with the
benchmark runner's exact invocation (`--disable-progress -V benchmark-data -mem
--terminal-width 200 -bs 60`). Order is balanced: odd rounds run the candidates
forward, even rounds in reverse, so drift inside a round is shared and its
direction alternates. The value recorded per run is the tool's own `TIMING total`
from the benchmark data, with `rss_peak` beside it. One host (Apple M1 Pro, eight
cores, Homebrew Perl 5.44), nothing else running.

**ScriptLog pair.** Base against `gate-40`, ten rounds, on
`ScriptLog.2025-04-09.1.log` (98 MB, 252,640 lines, the large single-file
ScriptLog in `docs/test-logs.md`), same invocation.

**Statement count.** NYTProf on the 100k-line access-log sample
(`tests/profile/samples/localhost_access_log-twx01-twx-thingworx-0.2025-05-07-100000.txt`)
for the base and for `gate-40`, run after the timing runs so the profiles do not
contend with them; the per-line statement count of `read_and_process_logs` must
differ by exactly 40 and no other sub may change.

**What is reported.** For each candidate and file: the median and the range of
ten rounds, and the delta against the base median in that same set of rounds.
The per-gate slope from the gate series by least squares over the four N values,
with its range from the round-to-round spread. The ceiling: slope times the
inventory count of run-constant tests on the every-included-line path. The hoist
probe's delta against that ceiling.

## Disposition

The measurement decides which of the two remedies, if either, is worth an issue,
and gives that issue its expected effect size and its before/after obligation.
Nothing here changes `ltl`: the probes live under `prototype/`, the record under
`tests/profile/results/342-read-loop-cost-curve/`, the assessment in the audit
report's item 8. If the slope is not resolvable at N = 40 the record says so
with the noise floor that prevented it, and the remedies are assessed on the
#567 numbers alone.
