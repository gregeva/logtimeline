## Findings against the hypotheses

**H1 (linear per-gate cost) holds.** The four medians of each gate series lie on
a line with residuals inside the round-to-round spread (±0.026 s on a 0.0175 s
per-test slope over N = 40, so the fit is resolved at every step, not only at
N = 40). Ten of ten rounds are positive at N = 10 on both files. One always-false
boolean scalar test on the every-included-line path costs **about 23 ns per line
on all three families** (23.0, 22.8 and 22.0 ns), which is the same absolute cost
per test everywhere.

**H2 (form is a cost class) holds.** A string compare costs 1.3 times a boolean
on the access log (30.1 against 23.0 ns per line) and 1.6 times on the
application log (36.3 against 22.8 ns); a hash lookup 1.4 times on both. The
str and hash series are above the gate series at every N on both files, with
per-round delta ranges that do not overlap the gate series at N = 40.

**H3 (the hoist recovers its share) holds on the access log and is not resolved
on the application log.** On the access log the hoist probe reads −1.20 % by the
medians and −0.078 s by the per-round median, negative in seven of ten rounds,
with a range crossing zero (−0.199 to +0.115 s). Its ceiling from the slopes is
about 1.3 %: ten string compares on the every-included-line path made cheaper by
(30.1 − 23.0) ns each, about 0.6 %, plus three empty `foreach` setups removed at
about one boolean each, about 0.6 %. The measured value is at that ceiling; the
spread of ten rounds is the same size as the effect, so the number is the
ceiling, not a precise reading. On the application log the hoist reads −0.01 %
(−0.015 s, negative in seven of ten rounds, range −0.054 to +0.047 s): nothing
resolvable, against a ceiling of about 1.0 % by the same arithmetic. Why the
application log recovers less than its ceiling was not investigated; the
retained-message path (where the five message-stats compares sit) is reached by
a smaller share of its lines than on the access log, and that share was not
measured.

**H4 (the family split follows loop share) holds in its mechanism and is
restated.** The absolute cost per test per line is the same on every family; the
percentage differs because the base cost per line differs: **11.6 µs per line on
the access log, 7.6 µs on the application log, 8.9 µs on the ScriptLog**. A fixed
23 ns per test is therefore 0.20 % of an access-log line, 0.30 % of an
application-log line and 0.26 % of a ScriptLog line. The #567 observation (access
logs regress, application logs do not) is not explained by this: on this base
the application log is the more sensitive family in percentage terms, and the
ScriptLog sits between. The #567 profile's "loop share" was a property of that
release's application-log path, and the prediction that ScriptLog behaves like
the access log is confirmed as "about the same absolute cost", not as a
percentage match.

## The ceiling

On the default scenario an included access-log line evaluates about 64 tests of
run constants (the inventory in the audit report's item 8, part 1: about 17
boolean scalars, 8 string compares, 6 `defined` tests, 4 hash or list truth tests,
and the numeric latches and precision tests), plus the two unconditional per-file
record blocks (about 24 statements) and the two per-message recomputations. At
23 ns per boolean-class test and 30 ns per string compare:

| what could be removed on the default scenario | tests | ceiling (access) | ceiling (application) |
|---|---|---|---|
| every run-constant test, at the boolean rate | 64 | 12.7 % | 19.1 % |
| the string compares converted to booleans (the hoist) | 8 to 10 | 0.6 % | 1.0 % |
| the three empty `foreach` setups (the hoist) | 3 | 0.6 % | 0.9 % |
| the `defined` tests on the twelve bound scalars | 6 | 1.2 % | 1.8 % |
| the option gates that are off on the default run (highlight, heatmap, histogram, expose, discard, mask, profile, count omit, UDM lists) | about 14 | 2.8 % | 4.2 % |
| the per-file record blocks under `-ni` | about 24 statements | not measured as a test class | |

These are upper bounds: they assume every removed test costs a full slope and
that removal costs nothing, and the loop's remaining work per line (about 11 µs
on the access log) is untouched.

## The two remedies, on paper

**(a) Generate the per-line body per run.** The loop body would be assembled from
blocks selected by the run's options and compiled once, as the scan sub is, so a
run naming nothing carries none of the option-shaped branches. Against the
ceiling: it can reach the 64-test bound only if every run-constant test is a
block boundary, which is most of them (the gates are `if` blocks). The seam
already exists (the scan sub returns an entry and the body starts), the
signature is the option set, and the registry's self-validation is the model for
proving a generated body (run the sample lines through it and compare the
record). The costs: a 1,300-line body as generated source, with the loop's
lexical state (about forty file-scoped and sub-scoped variables it reads and
writes) either hoisted to file scope or threaded through; debugging a body that
exists only inside an `eval`; and every future change to the loop written as
source-string edits. The measured prize on the default scenario is at most about
13 % on the access log and about 19 % on the application log, and less on any
run that turns options on, because those branches are then needed. This is a
design change of the size the #567 disposition named; the measurement gives it
its expected effect.

**(b) Hoist per-line option handling.** The measured floor is the hoist probe:
about 1 % on the access log, unresolved on the application log, for fifteen
substitutions and three wraps. The remaining hoistable items (the twelve bound
`defined` tests behind one `$numeric_filter_active`, the off-by-default gates
grouped behind one boolean per feature block, the millisecond bucket size and
the key length computed before the loop, the per-file record blocks behind
`!$no_index`) add up to a ceiling near 5 % on the access log and 7 % on the
application log by the table above, each item a small behaviour-neutral change
with its own before/after. This is the shape the demand-gate pattern already
takes; it costs no generation machinery and keeps the loop readable.

## Disposition

The per-test cost is now a number: **about 23 ns per line for a boolean test,
30 ns for a string compare, on every family**, and every gate added to the loop
costs its share of that on every line whether or not it fires. The remedies are
assessed for the architect: (b) is a sequence of small measured changes worth
about 1 % each on the access log (the hoist probe is its first step and is
already proven neutral); (a) is worth at most 13 % on the access log on the
default scenario and carries the generation cost. Nothing in this record changes
`ltl`; the probes, the driver and the summariser stay under `prototype/` as the
method for the next per-line question.
